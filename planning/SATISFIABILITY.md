# Execution satisfiability

This is a bounded manual conformance check for the hard-prerequisite semantics in `CONVENTIONS.md`. It adds no node/edge syntax, solver, authority source or publication protocol. Use the accepted node contracts in `NODE_CONTRACTS.md`, qualified identities in `REFERENCES.md`, and inherited readiness in `NESTING.md`.

## Invariant and two separate conclusions

Reject a direct hard-prerequisite self-dependency: X cannot require X, a Gate cannot count itself as its own input, and a Decision outcome cannot return directly to that same Decision. Longer cycles are evaluated by the rule below, not automatically classified as self-loops. Reject an unavoidable cycle among unmet prerequisites when every possible way to satisfy the required inputs depends on work that those same inputs prevent from starting. Such a scope is not execution-satisfiable and MUST NOT be treated as dispatchable. A valid Role assignment, an INPROGRESS label, or a passing shape/style checklist cannot cure this defect.

A visual cycle alone is not the test. An explicit OR or N-of-M Gate may have enough independently attainable inputs to break the circular wait. Conversely, finding one runnable node elsewhere in a plan does not establish that a separate required component can progress.

Record separately:

- **Dependency feasibility:** a finite, non-circular ordering of prerequisite satisfaction for the named scope, with its exact assumptions, or a diagnosed cycle/closed boundary/unknown. A hypothetical ordering says nothing about whether the work will succeed.
- **Ready now:** the proposed action's prerequisites are actually satisfied in current accepted state, with current objective evidence and all independent operational/authority checks passed. Hypothetical future work, acceptance, publication or artifact usability is never dispatch evidence.

For example, an unfinished M1 with no predecessors may be structurally attainable, allowing a feasibility witness for M1 then M2. M2 cannot start until M1 actually has valid acceptance and the current accepted roadmap projects DONE and indexes it. A feasibility mark is not a status change or acceptance record.

## Scope and dependency interpretation

At plan-change review, bind the exact candidate and accepted predecessor, and examine every changed dependency/node predicate/status/operative selection plus all affected prerequisite and consumer paths. Include every Gate alternative needed to justify an escape; do not truncate the walk at the changed line. Record required current outcomes, deferred outcomes and their reasons. Do not describe the whole plan as feasible when only a component was checked.

Before first substantive dispatch, resumption or another obligation-creating action, use the current accepted PlanRef/publication event and applicable evidence. Record this check in the existing attempt/inventory `current_validation_evidence_and_conclusion`, separately from the immutable package `plan_ref`. Reuse an earlier analysis only after validating that its dependency definitions, selections, evidence and assumptions still apply; relevant changes require a new check. Candidate analysis does not make the candidate current.

Build the dependency view as follows:

| Input | Interpretation |
|---|---|
| Ordinary hard incoming edges | AND: every applicable prerequisite is required. |
| Gate inputs | Use the exact objective predicate: OR needs a sufficient alternative; N-of-M needs N distinct eligible inputs out of the declared M. Do not convert them all to AND or count an input twice. Preserve additional constraints in the predicate. |
| Decision outcomes | Under adopted `decision-result-v1`, only tokens in the exact valid current indexed selection are open. Keep an unselected/no-result edge as a **closed guard** on its destination; deleting it must not turn that destination into a free starting node. |
| Branch membership/rejoin | Use explicit accepted outcome mappings and rejoin predicates. An unselected branch is not required current work merely because it is drawn, but its output cannot be silently removed from an ordinary downstream AND or counted by a selected-only Gate. Ambiguous applicability blocks the affected conclusion. |
| Milestone/DATA/Gate facts | Apply their own satisfaction rules; distinguish actual current evidence from a hypothetical later satisfaction step. Expired, unavailable, wrong-revision, withdrawn or unindexed evidence is not an actual seed. |
| Cross-plan/ancestor boundary | Resolve the compatible accepted boundary and full ancestor readiness under `NESTING.md`. Bind current parent state separately from relationship pins. For opaque portions use only explicit accepted boundary/readiness evidence, never invented internals. |
| `assigned to`, `decides`, delegation/authority edges | Exclude from dependency-cycle analysis. Their independent authority/assignment validity checks still apply. |
| Dotted `preferred before` edges | Exclude: these do not block a start. |

A Decision's authorized research/preparation is checked against its own prerequisites. It does not need a fictional Milestone or open any outcome. With `active_result: none`, downstream work is waiting for a valid accepted selection, not a reason to guess a branch. A proposed activation/replacement may be analyzed as an explicitly labeled candidate scenario; repeat against actual accepted state before dispatch. Never combine mutually exclusive selections or successive replacements in one witness. A currently unselected branch must be rechecked before any later activation, including its previously deferred cycles.

## Manual procedure

1. **Fix the frame.** Record plan/object identities, exact accepted PlanRef/event, candidate if reviewing a change, supported grammar/node contracts, required scope and current Decision selections. Inventory actual satisfied inputs, unmet inputs, external/opaque conditions, and applicable authority/operational blockers. Reject self-dependencies anywhere in the reviewed declared dependency scope, regardless of status; flag unrelated defects separately rather than claiming they were checked away.
2. **Establish actual seeds and permitted transitions.** Only validated current satisfaction is an actual seed. Separately list evidenced, authorized ways an unmet input could become satisfied without circular execution: for example a legal producer start followed by successful delivery/acceptance/publication, or projection of an already valid receipt. For an external input, state its independently attainable source/conditions; an unexplained promise is unknown. Do not assume a missing grant, changed predicate, unselected result or unsatisfied ancestor can be waived.
3. **Construct a finite witness.** For ordinary positive AND/OR/at-least-N predicates, repeatedly mark an unmet item *attainable* only after its required inputs have actual seeds or earlier attainable marks. For an ordinary executable node, all prerequisites must qualify; record its hypothetical execution and required acceptance/projection or resolution step before its output can count. For a Gate, record the exact sufficient input set and predicate evaluation. A valid selected Decision edge can qualify only with its governing conditions; hypothetical research cannot mint an operative selection. Stop when a pass adds no mark. Keep the justification for each mark so it can be expanded into an ordered sequence; simultaneous mutual assumptions are not a witness.
4. **Inspect the residue.** For each required unmarked item, trace why each permissible sufficient input set failed. A closed Decision branch, unresolved external condition, missing authority or opaque evidence is a named blocker, not automatically a cycle. Diagnose a cycle only when a nonempty set of unmet items has no valid seed/independent transition and every permitted satisfaction route for each member still requires a member of that set. Record the exact circular wait and the failed Gate alternatives. A cycle blocks its dependent scope; an independent component may proceed only with its own complete checks. Never bootstrap the set by assuming all its members true at once.
5. **Validate the witness and decide readiness separately.** Walk the ordered witness against the actual predicate definitions and explicit state-transition rules. Then check the intended next action using only actual current satisfaction, all current execution/authority/fence/revocation checks, and the full applicable ancestor chain. Record feasible-but-waiting, blocked-cycle, blocked-condition or unknown as appropriate, plus ready/blocked for the specific action. Unknown or blocked prerequisites do not permit dependent dispatch. A structurally feasible plan may still be no-dispatch under `transition_action_contract: none`.

The marking shortcut assumes monotone positive input predicates: adding a satisfied input cannot make a previously true predicate false, and counted facts remain compatible across the proposed sequence. The grammar also permits other explicit objective predicates. For exact-count, negative, expiring, consumable or otherwise state-sensitive conditions, supply a finite state-by-state witness and re-evaluate every affected predicate at each step; do not union facts that cannot hold together. If that cannot be established within the bounded manual analysis, record **unknown** and keep affected execution blocked pending clarification/replan. This document does not claim a complete decision procedure for arbitrary predicates, timing, resource constraints or all future Decision outcomes.

Already issued valid acceptance awaiting projection, or independently authorized continued work with sufficient evidence, may provide a genuine non-circular transition. Record and validate it explicitly; a status label or an imagined future acceptance cannot substitute. This requires an actually permitted transition under the existing contracts, not a new exemption: a continuation disposition cannot reopen an unselected branch for new dispatch or waive a currently applicable hard prerequisite. Do not retrospectively treat that future projection as current. If a later publication/reopening/withdrawal invalidates a seed or changes a predicate, re-evaluate the affected closure before relying on it.

## Rework, adoption and plan changes

Feedback is ordinarily later work: define a distinct outcome/iteration with its own stable identity, or publish an explicitly authorized reopening/replan/state transition under the existing lifecycle rules. Preserve earlier acceptance/results and their original contract bindings. Show a finite order from the newly accepted starting state. Adding M2 as a prerequisite of starting the same unfinished M1 that M2 already depends on is not an iteration. Neither the word `rework` nor a scheduling preference can waive a hard prerequisite.

Record the conformance analysis with the normal plan-change evidence using `templates/PLAN_CHANGE.md` and the GitHub plan-change form. Include scope, exact states/selections, seeds, sufficient Gate input sets, ordered witness or residual blockers, next-action readiness and limitations. Recheck changes to dependencies, Gate predicates, Decision activation/replacement/revocation, DATA validity, and Milestone completion/reopening that affect the analysis. Candidate feasibility is review evidence, not approval/publication authority. A change can retain explicitly deferred or blocked planning scope, but cannot claim it dispatchable; active-work consequences still require the existing complete manifest/fence/receipt handling.

Existing projects adopt this conformance requirement through accepted planning change under prior governance. Record the affected current graph, unresolved dependencies and active-work disposition; apply the check before dependent dispatch/resumption after adoption. Preserve historical PlanRefs, receipts and prior semantics without backdating checks or implying earlier dispatch was validated by this procedure. No new grammar version or automatic interpretation of unsupported node/boundary contracts is introduced. Future selection or replan must actually become accepted before its changed prerequisites govern work.
